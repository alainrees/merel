# Mailcraft architecture

| Layer | Crate | Job |
|---|---|---|
| L1 | `secrets` | Passwords in the system credential store (Keychain, Credential Manager, Secret Service) through `keyring`; a memory store for tests. Secrets are zeroed on drop and hidden from `Debug`. |
| L1 | `model` | Accounts, folders, message headers, addresses, calendars, appointments, contacts and tasks. Validates everything that comes from the network or the keyboard (address shape, header length, control characters, appointment times). No I/O. |
| L2 | `mime` | Header and body parsing through `mail-parser`. The HTML part becomes a layout tree through `html`, with a plain-text rendering (`html2text`) next to it for previews and replies; pictures the HTML refers to by content id travel along (4 MB each at most) and leave the attachment list. Input is bounded at 8 MB. |
| L2 | `html` | HTML mail reduced to a small layout tree (paragraphs, headings, lists, quotes, tables, rules, preformatted text, emphasis, links, pictures) by walking html5ever's parse against an allow-list: scripts, styles, forms, frames, objects, hidden blocks and every other attribute are dropped; a link keeps only an `http`, `https` or `mailto` target; a picture stays a reference (`cid:` part, decoded `data:` URL, or a counted remote URL that is never fetched). Depth and node count are bounded. No CSS is interpreted. |
| L2 | `imap` | Blocking IMAP client over rustls (implicit TLS or STARTTLS, platform certificate verifier, no way to disable checks): folders with SPECIAL-USE, newest headers with BODYSTRUCTURE, `BODY.PEEK[]`, flags, MOVE with COPY fallback. Mailbox names are quoted; CR/LF are refused. |
| L2 | `smtp` | Sending through `lettre` over rustls (implicit TLS or STARTTLS, platform verifier), plain-text messages with Date, In-Reply-To and References; the Message-ID is minted under the sender's domain so the computer's host name never goes on the wire. |
| L2 | `mailbox` | The `Mailbox` trait every mail store implements (folders, headers in pages of the newest `limit` after an `offset`, bodies, flags, moves, send, and `create_folder`/`rename_folder`/`delete_folder`), with opaque string ids so the engine never knows whether it talks to IMAP or EWS; and `ItemStore`, which a store that also keeps appointments, contacts and tasks offers through `Mailbox::items`. |
| L2 | `exchange` | Exchange Web Services over HTTPS (`ureq` + rustls, platform verifier): `FindFolder`/`GetFolder`, `FindItem`, `GetItem` with MIME content (parsed by `mime`, like IMAP mail), `UpdateItem`, `MoveItem`, `CreateItem` to send. Calendar, contacts and tasks as an `ItemStore`: `FindItem` (a `CalendarView` for appointments) for ids, `GetItem` in batches for fields and body, `CreateItem`/`UpdateItem`/`DeleteItem` to write back; the request header names the computer's time zone (IANA name mapped to the Windows name) so all-day appointments and due days land on the right day. Every request value is XML-escaped; replies are size-capped and read with a read-only parser. Basic or Bearer authentication only; NTLM is reported, not spoken. |
| L2 | `google` | Gmail accounts: wraps the IMAP client and adds Google's Calendar, People and Tasks APIs as an `ItemStore` behind the same OAuth token (`ureq` + rustls, platform verifier), when the token carries the three scopes; otherwise mail only. Ids go into URLs percent-encoded, replies are size-capped, a 401 is reported as a refused login so the worker fetches a fresh token. Store ids carry their kind (`event:`, `people/`, `task:`), since the APIs are three. |
| L2 | `graph` | Microsoft 365 through Microsoft Graph, mail included: well-known folders by name, `mailFolders` and one level of children, `messages` with `$select`, raw MIME through `$value` (parsed by `mime`), `isRead`/`flag` patches, `move`, `sendMail` with base64 MIME; `calendarView`, `contacts` and the default To Do list as an `ItemStore`. One OAuth resource, so one sign-in covers everything; Exchange Online drops EWS in October 2026, which rules the `exchange` crate out for it. Replies are asked for in UTC with text bodies; ids are percent-encoded; a 401 is a refused login. |
| L2 | `dav` | IMAP accounts with a CalDAV/CardDAV server next to them (Fastmail, iCloud, Nextcloud, Posteo, mailbox.org, self-hosted): wraps the IMAP client and adds the server's calendars, address books and task lists as an `ItemStore` behind the same user name and password (Basic over HTTPS, platform verifier). Discovery per RFC 6764 (`/.well-known/caldav`, `current-user-principal`, the home sets, the collections). `ical.rs` reads and writes iCalendar and vCard: time zones through `chrono-tz`, lines folded at 75 octets, and a change is written back into the resource as it was read, so alarms, attendees and photos Mailcraft does not model survive; `If-Match`/`If-None-Match` guard every PUT. Recurring appointments come expanded from the server and are read-only. Redirects are followed by hand (same method, `https` only), replies are size-capped and parsed read-only; a 401 is a refused login. Store ids are the resource URLs with a kind prefix. |
| L2 | `store` | The offline cache: per account, the folders, message list, opened messages (raw, up to 300 or 64 MB), synced calendar, contacts and tasks, as one file sealed with ChaCha20-Poly1305 (`aws-lc-rs`, the library behind rustls) under a random key kept in the system keychain; the account id is bound in as associated data. A file that does not open is ignored, never shown. The server stays the truth and nothing is written back to it. |
| L2 | `oauth` | OAuth 2.0 authorization-code flow with PKCE (RFC 8252): the system browser signs in, a loopback listener on `127.0.0.1` with a random port receives the code once, `state` is checked, tokens are fetched over rustls. No embedded web view; only the refresh token is stored (keychain). |
| L3 | `engine` | `Session` (state and selection) and the command registry: every action is a `CommandSpec` with an id, run through `Session::run`, which validates parameters and never panics on bad input. One worker thread per account speaks IMAP/SMTP (with CalDAV/CardDAV next to it when the account names a server), EWS or Graph with a password or an OAuth access token refreshed on demand (a Microsoft 365 account whose scopes name Graph takes the `graph` crate, an older one IMAP), and mirrors the account's appointments, contacts and tasks when its store keeps them (`sync`). Every two minutes the engine refreshes the inbox of each connected account and the selected folder, asking for as many headers as are listed so pages loaded with "older messages" stay, and counts unread messages that were not listed before; every five minutes it asks the stores for their items again. `cache` fills the session from the `store` crate on start, serves opened messages from it, and writes dirty accounts a couple of seconds after each server answer or command, and when the window closes. Removing an account stops its worker, deletes its keychain entries and its cache file, drops everything the session held of it (a late report from the stopped worker is ignored) and rewrites the accounts file. Built-in sample mail. Drafts put aside (`drafts.rs`: `StoredDraft` per account, `draft.save`/`draft.delete`) travel with the account's encrypted cache snapshot and never reach a plain file or the server. |
| L4 | `ui-egui` | Outlook-style front end drawn with egui: tab strip and ribbon, module rail (Mail, Calendar, People, Tasks), folder pane, message list with Outlook's keyboard shortcuts (arrows walk the list, Delete, Ctrl/Cmd+N, R, Shift+R, F, Shift+V for "Verplaatsen naar", Q, U, E for the search box, Esc, F5; none fires while a text field has the keyboard or a message is being written, so typing never triggers one) and a search box (every word must occur in subject, sender, recipients or preview; current folder or all folders, over the headers already fetched; a "Zoek op de server" button asks the server of the selected folder, which also looks in older mail and in message text: IMAP `UID SEARCH TEXT` per word, EWS `FindItem` with a `QueryString`, Graph `$search`; what it finds is listed next to the local matches for as long as the box holds those words), reading pane, status bar; a "Help" tab (`help.rs`: the shortcut list, the settings folder and project page opened with `open`, "Over Mailcraft"); a message row is a drag source (`DraggedMessage`) and every folder row a drop target, so a message can be dragged to a folder, and "Verplaatsen" opens a window with the folders of the message's account (`message.move { folder_id, id? }`, same account only, the server gets `Job::Move`); a "Map" ribbon tab and a right-click menu on every folder row (`folders.rs`) open one small window to make a folder under the selected one, rename it, confirm its removal or its emptying, or confirm that a message in the Deleted folder goes for good, and mark a folder's mail read; a "Categoriseren" menu, coloured squares on the rows, chips above the open message and the "Alle categorieën" window (`categories.rs`); a "Beeld" tab (`view.rs`) with the list filter and order, the reading pane's place (the message list is a left or a top panel around the same `message_list`), compact rows and the theme (`Context::set_theme`); calendar with month, week and day views and an appointment window (`chrono` for dates and the local time zone; repeat rows for how often, which weekdays and when it ends, a 🔁 mark on every occurrence, and "Deze keer overslaan" when the window was opened from an occurrence; a "Herinnering" choice); a reminders window (`reminders.rs`) anchored top right whenever `Session::due_reminders` has something, each with "Begint over …"/"Begon … geleden", "Openen", "Sluiten" and "Uitstellen…", asking for the window's attention once per new reminder. Light and dark theme tokens in the ArtCraft style. The reading pane draws the `html` layout tree with egui's own text engine (`html.rs`): links open in the system browser on click and show their real target on hover, a `mailto:` link opens the compose window, embedded pictures are decoded by the `image` crate (PNG, JPEG, GIF, WebP, BMP; no SVG) and forgotten when the next message opens, an attachment chip saves the file to the Downloads folder under a cleaned name and never over an existing file (`attachments.rs`; nothing is opened or run); remote pictures get a placeholder until the person clicks "Afbeeldingen laden" for that one message (`remote.rs`: a thread per picture with `ureq`, `https` only including redirects, 20 s timeout, 5 MB cap, at most 40 pictures, the reply must be an image; everything is dropped when another message opens). The compose window takes attachments from the computer's own file dialog (`rfd`: native on macOS and Windows, the desktop portal on Linux) or from files dropped onto the window; each is read once, named by its last path segment only, typed by its extension (`model::mime_of`), and the lot is capped at 25 MB (`model::MAX_ATTACHMENTS`), checked again when `smtp::build` makes the `multipart/mixed` message that every account kind sends. Closing the window (or "Opslaan als concept") puts what was written aside through `draft.save`; an untouched window (`Compose::is_blank` compares against what it opened with) leaves nothing; `drafts_list` shows an account's drafts in place of the message list, to open or drop them. |
| apps | `mailcraft` | Desktop app (eframe + wgpu). |

## Folders

`folder.create { name, parent?, account_id? }`, `folder.rename { id, name }` and `folder.delete { id }` (`engine::folders`) let a person make a folder under another one (or at the top of the account), rename an ordinary folder or remove it; special folders (`FolderKind` other than `Other`) are refused with `Param("id")`. A name is cleaned, trimmed, at most `MAX_FOLDER_NAME` characters and holds no `/` or `\`; the IMAP client also refuses the server's own hierarchy delimiter and the `%`/`*` wildcards. The sample account changes in place. A real account gets `Job::CreateFolder`, `Job::RenameFolder` or `Job::DeleteFolder`; these are not kept offline (the person is looking at the folder list, so the server has to answer now). The worker runs the change and lists the folders again, and `Event::Folders` replaces the account's folders through `Session::set_folders` (shared with `Event::Connected`), dropping the messages of folders that are gone; when the selected folder was renamed or removed, the inbox is selected and refreshed. IMAP: `CREATE` under the parent with the delimiter `LIST` reports for it (then `SUBSCRIBE`), `RENAME` keeps the parent part of the path, `DELETE` after leaving the folder when it was the selected one. EWS: `CreateFolder` under a `FolderId` or `msgfolderroot`, `UpdateFolder` with the folder's change key from `GetFolder`, `DeleteFolder` with `SoftDelete`. Graph: `POST /me/mailFolders` or `…/childFolders`, `PATCH displayName`, `DELETE`.

`view.filter { filter }` and `view.sort { sort }` (`engine::view`) set `Session::filter` (all, unread, flagged, attachments) and `Session::sort` (newest, oldest, sender, subject), and `view.category { name? }` sets `Session::category_filter`, which `visible_messages` applies after the search; the "Beeld" tab (`ui-egui::view`) runs them and keeps its own choices (reading pane right or below, compact rows, light/dark/system theme, the sort) in `view.json` next to the accounts file through `config::view_path`, applied again at start.

`folder.empty { id? }` removes every message of a folder from the session and queues `Job::Empty` (kept offline like a move), which the store runs on the whole folder, listed or not: IMAP `STORE 1:* +FLAGS \Deleted` and `EXPUNGE`, EWS `EmptyFolder` with `SoftDelete`, Graph a `DELETE` per message over the pages `list` fetches. `folder.mark_all_read { id? }` marks the listed unread messages read through `Session::flag_message`, one `Job::Flag` each. `message.delete` on a message whose folder is the Deleted one removes it for good (`commands::delete_message`, `Job::Delete`: IMAP `\Deleted` plus `UID EXPUNGE`, EWS `DeleteItem` with `SoftDelete`, Graph `DELETE /me/messages/{id}`); the UI asks before running it (`MailApp::run` turns such a `message.delete` into the "Definitief verwijderen" window), as it does before `folder.empty` and `folder.delete`.

## Categories

`model::Category` is a name and a `CategoryColor`; `MessageHeader::categories` holds names. `engine::categories` keeps the person's list in `Session::categories`, saved to `categories.json` by `Engine::persist` (a missing file gives Outlook's six, an emptied list stays empty), with `category.save { name, color }` (new, or a new colour) and `category.delete { name }`; `message.categorize { name, id? }` toggles a name on a message and `message.clear_categories { id? }` takes them all off. Each change queues `Job::Categories { categories, removed }`, a change kept offline like a flag; `Mailbox::set_categories` gets the whole new set and what came off. IMAP keeps them as keywords: `category_keyword` turns a name into an atom (letters, digits, `-`, `.`; the rest, spaces included, becomes `_`, read back as a space), `+FLAGS`/`-FLAGS` set and clear them, and keywords starting with `$` and the junk markers are not categories. EWS lists `item:Categories` in `FindItem` and sets it with `UpdateItem`; Graph selects and patches `categories`. The UI (`ui-egui::categories`) draws a square per category on a message row, chips above the open message, a "Categoriseren" menu in the ribbon and the "Alle categorieën" window; a name this computer does not know is grey.

## Mail rules

`model::Rule` is one condition (a `RuleField`: sender, recipients, subject or any of those plus the preview, and the text it must contain, compared without regard to case) and up to four actions (move to a folder of the same account, mark read, flag, give categories), bound to one account. `engine::rules` keeps them in `Session::rules`, saved to `rules.json` by `Engine::persist` like the other local files, with `rule.save`, `rule.delete` and `rule.run` commands; removing an account drops its rules. `Session::apply_rules` does what a person would: it changes the header in the session at once and queues `Job::Flag`/`Job::Move`/`Job::Categories` for the server (never for the sample account), so a rule works offline and replays like any other change; the first rule that moves a message ends the run for that message. The `Event::Headers` arm applies the rules to messages an inbox refresh lists that were not listed before (not on the first listing of a folder, so an existing inbox is not reshuffled on the first start), and counts them in `rule_hits` for the status bar; `rule.run` goes over every listed message of a folder, whatever its kind. The UI (`rules.rs`) has the window with the list, the form (`Form`, with the folders of the chosen account except its inbox), "Regel voor deze afzender" prefilled from the selected message, and "Regels nu uitvoeren op deze map".

## Quick steps

`model::QuickStep` is a name plus the same actions a rule has (move to a folder of its account, mark read, flag, categories), bound to one account; `validated` cleans the name and the category names and wants at least one action. `engine::quicksteps` keeps them in `Session::quick_steps`, saved to `quick_steps.json` by `Engine::persist` and dropped with their account, with `quickstep.save`, `quickstep.delete` and `quickstep.run { id, message_id? }`; running one changes the session at once and queues `Job::Flag`/`Job::Categories`/`Job::Move` like the person doing it by hand, marks and categories first and the move last, so a folder that is gone (`Param("move_to")`) still leaves the rest done. The UI (`quicksteps.rs`) shows a small button per step of the selected message's account in the "Snelle stappen" group of the "Start" tab, the "Beheren…" window with list and form, and `MailApp::run_quick_step` for Ctrl+Shift+1 to 9.

## Calendar

Appointments are session state like messages: `Session::appointments` plus `appointment.select`, `appointment.save`, `appointment.skip` and `appointment.delete` commands, each validated in `model`. The engine saves `calendar.json` (owner-only, written through a temporary file) right after a command changes it. Times are Unix seconds in UTC; only the UI converts to the computer's time zone, so a file moved between machines keeps its moments. A recurring appointment is one entry with a `model::Recurrence` (RFC 5545's vocabulary: frequency, interval, weekdays, until or count, skipped occurrences), validated so an occurrence is shorter than the gap to the next; `Session::appointments_between` expands it with `Appointment::occurrences` on the computer's clock (`chrono::Local`), so a weekly 10:00 stays 10:00 across a daylight-saving change and a monthly 31st falls on the last day of a shorter month; at most 5 000 occurrences per series per expansion. A new appointment on an account calendar may carry a recurrence as well: the rule is written once, with the item (`Recurrence::rrule` gives the iCalendar `RRULE` for CalDAV and Google, with a `TZID` start or the zone named so the series follows the wall clock; `exchange::items::recurrence_xml` the EWS pattern and range; `graph::recurrence_json` the `patternedRecurrence`), after which the server owns the series and hands over single occurrences, so `appointment.save` refuses a recurrence on an existing account appointment. Skipping an occurrence adds its start to the rule's `skipped` list; deleting the appointment removes the whole series.

Reminders (`engine::reminders`): `Appointment.reminder` is minutes before the start (`model::MAX_REMINDER` four weeks), for a series before every occurrence. `Session::due_reminders(now)` expands the appointments with a reminder over a window of a day back to four weeks ahead and keeps the occurrences whose reminder moment has passed, that started less than a day ago, and that were neither closed nor put off; the UI asks it every frame (the calendar is small) and repaints at least every five seconds while something is due. `reminder.dismiss { id, start }` records a `ReminderKey` in `Session::dismissed_reminders`, saved in `calendar.json` for account appointments too (the servers do not record this) and pruned a day after the occurrence; `reminder.snooze { id, start, minutes }` keeps the moment to come back in memory only, so a put-off reminder returns after a restart, as in Outlook. The stores carry the reminder as the server's own: EWS `ReminderIsSet`/`ReminderMinutesBeforeStart`, Graph `isReminderOn`/`reminderMinutesBeforeStart`, Google `reminders.overrides` (a pop-up; no reminder hands the event back to the calendar's defaults, which the event itself does not name, so such an event shows none here), CalDAV a `VALARM` with a negative `TRIGGER` from the start (alarms at an absolute time or relative to the end are left as they are). An account whose store keeps a calendar (Exchange) gets a calendar of its own in the session, see Account items below; the local calendar stays as the fallback. Exchange, Gmail, Microsoft 365 and an IMAP account with a CalDAV server have one.

## Contacts

Contacts follow the calendar's pattern: `Session::contacts` with `contact.select`, `contact.save` and `contact.delete`, validated in `model` (every address must parse), saved to `contacts.json` right after a command changes them. `Session::suggest_addresses` serves the compose window: contacts first, then addresses seen in the session's mail, matched on the start of a word or of the address. A contact carries the account it lives in (`None` for this computer); the form asks where a new one goes when there is a choice. Exchange, Gmail (People API), Microsoft 365 and an IMAP account with a CardDAV server have one.

## Tasks

Tasks follow the same pattern: `Session::tasks` with `task.select`, `task.save`, `task.complete` and `task.delete`, validated in `model`, saved to `tasks.json`. A due day is stored as local midnight in Unix seconds, so "overdue" is a plain comparison with today's midnight. Open tasks sort by due day, then priority; done ones by completion. Tasks carry their account like contacts do. Exchange, Gmail (Tasks API, which has no priority), Microsoft 365 (To Do) and an IMAP account with a CalDAV server that accepts VTODO have one.

## Account items

`engine::sync` mirrors the appointments, contacts and tasks of an account whose `Mailbox` offers an `ItemStore` (Exchange; Microsoft 365 through Graph; Gmail when its token has the scopes). An account signed in earlier gets the current scopes and servers through "Opnieuw aanmelden" in the Backstage: `Engine::sign_in_again` runs the browser sign-in with the preset and the account is replaced in place. When such an account connects (`Event::Connected { syncs_items: true }`) the engine queues `Job::Sync` for a window of 90 days back and 400 days ahead; `sync.refresh` (the Refresh button in the calendar, contacts and tasks ribbons) asks again. `Event::Synced` replaces the account's items in the session. Session ids of account items are `<account id>/<store id>`, like folder ids, so an id always says where an item lives, and the local files (`calendar.json`, `contacts.json`, `tasks.json`) receive local items only. A command on an account's item changes the session at once and leaves `Job::SaveItem` or `Job::DeleteItem` for the store; a new item carries a pending id until `Event::ItemSaved` brings the store's id, and editing it before then is refused rather than duplicated. All-day appointments and due days come back from a store as midnight in its time zone; the engine snaps them to the nearest local midnight. Account items are part of the offline cache (see below), so without a connection the modules show what the account had last time.

## Offline cache

`engine::cache` keeps the `store` crate in step with the session. On start every account's cached state (folders, message list, opened messages, calendar, contacts, tasks) is put in the session before any server answers, so the window is usable at once, and stays usable without a connection; the account shows "Verbinden…" until the server answers, and whatever the server reports replaces the cached state (folders that no longer exist take their messages with them; the selected folder's list is refreshed). Opening a message the cache holds needs no connection: the raw message is parsed again as if the server had sent it.

Changes made without a connection (flags, moves, deletions, items saved or deleted) are not lost: the worker hands a job it cannot connect for back as `Event::Deferred`, the session applies the change as if it had succeeded and counts it in `queued` (the status bar says how many changes wait), and the cache keeps the job in its `pending` list, so it survives a restart. The worker tries the server again on its own, 15 seconds after a failure and then at doubling intervals up to 5 minutes; when it connects, `Event::Connected` makes the engine put the queued jobs ahead of everything else, so they reach the server before the folder list is refreshed. A queued job that finds no connection again is queued again; one the server refuses for another reason is reported and dropped, and the next listing shows the server's state. Sending waits in no queue: a message that cannot go out is reported on the draft, and the person sends it again. Message ids are stable across runs (`<account>/<folder path>#<server id>`), which is what makes a cached message findable.

## OWASP top 10 mapping

| Risk | How Mailcraft handles it |
|---|---|
| Injection | Addresses and headers validated in `model`; SQL through parameterised queries only; IMAP/SMTP commands built from typed values, never string concatenation |
| Broken authentication | OAuth2 + PKCE where offered; passwords only over TLS; keychain storage |
| Sensitive data exposure | The offline cache is sealed with ChaCha20-Poly1305 under a key in the system keychain and written owner-only; no telemetry; remote content blocked; logs never contain addresses or bodies |
| XML/XSS-class issues | No browser engine: HTML is parsed into a layout tree against an allow-list and drawn by egui, so nothing in a message can run, load or style the window; links open only `http`, `https` and `mailto` targets, through the system browser, and show their real target on hover |
| Security misconfiguration | Secure defaults only: no plain-text option, certificate checks cannot be disabled in the UI |
| Vulnerable components | `cargo audit` and `cargo deny` in CI; pure-Rust dependencies preferred |
| Integrity | Signed releases; S/MIME and PGP verification shown clearly in the reading pane |
| Logging | Command ids and errors are logged; content is not |
| SSRF-class issues | Only user-configured hosts are contacted; nothing in mail content is fetched on its own. Pictures on the internet load only after a click, per message, over `https` only, size-capped |
